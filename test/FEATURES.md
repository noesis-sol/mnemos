# Features and their tests

mnemos is an MCP server (TypeScript, Node >=22.13, npm) that reads a browser's bookmarks
(Chrome's `Bookmarks` JSON and the other browsers' files; it never writes them) and answers six
MCP tools over stdio. Five are keyword tools over the file, in `src/lib.ts` (`src/browsers.ts`
and `src/plist.ts` for the other browsers); the sixth, `semantic_search` (`src/semantic.ts`),
reads a local index (`src/index-store.ts`, `node:sqlite` in the cache directory) that the
server fills in the background: bookmark titles embedded by a local model (`src/indexer.ts`,
`src/embedder.ts`, with the runtime installed on first use by `src/runtime.ts`), then the
bookmarked pages fetched under a fixed policy (`src/fetcher.ts`, `src/fetch.ts`,
`src/extract.ts`, `src/pdf.ts`, `src/headless.ts`, `src/policy-proxy.ts`), cut into chunks
(`src/chunk.ts`) and embedded too. `src/index.ts` is the MCP wiring, `src/icon.ts` is generated by
`scripts/build-icons.mjs` from `assets/`. Tests use Node's built-in runner (`node:test`) against
the compiled `dist/` and synthetic fixtures in `test/fixtures/` (chiefly `bookmarks.json`),
injected through `CHROME_BOOKMARKS_PATH`; tests that start the server set `MNEMOS_CACHE_DIR` to
a temporary directory and `MNEMOS_EMBEDDER=fake`, and serve pages from `127.0.0.1` when they
fetch any.

Freshness: adds, then deletes and renames, bookmarks while the server runs. Prints a report and appends it to `$GITHUB_STEP_SUMMARY` (9 tests, ~2.5 min with the model in `MNEMOS_E2E_MODEL_CACHE`, ~2 min 40 s without it, as `scripts/check-full.sh` runs it, downloading the model into its scratch cache; most of it the pages fetched one per second) |

`npm test` runs `node --test` with no file arguments, so Node's runner discovers the test
files: a new file named `test/<feature>.test.js` runs with no edit to `package.json`. On every
supported Node (checked on 22 and 24, which match glob patterns) the runner skips `node_modules/` and runs every `.js` file under `test/` and
every `*.test.js`, `*-test.js`, `*_test.js`, `test-*.js` or `test.js` elsewhere, `dist/`
included. So keep helper modules out of `test/` or give them no top-level side effects, and
keep test files out of `src/` (tsc would copy them into `dist/`, where they would run too).
Suites too slow for `npm test` live in `e2e/` with names none of those patterns match
(`<feature>.e2e.js`), and `scripts/check-full.sh` runs each by path.

Runner times on macOS, Node 24, with `node_modules` installed and `TUTTI_CORES=5`, which
check-fast passes on as `--test-concurrency` (2026-10-23):

- `scripts/check-fast.sh`: 28–30s over three runs (build, then 658 tests in ~26s)
- `scripts/check-full.sh`: about 3 min 40 s: check-fast (~30s), the published package (~2s),
  the embedding model (~30s, most of it the model's download into a fresh cache) and the
  semantic search acceptance (~2 min 40 s, most of it pages fetched one per second); both model
  suites run, since the runner sets `MNEMOS_E2E_MODEL=1`, so check-full needs the network (the
  model from Hugging Face, the package's dependencies and the embedding runtime from npm's
  registry)

CI (`.github/workflows/ci.yml`) runs `npm ci`, `npm test` and `node --test e2e/package.e2e.js`
on ubuntu, macOS and Windows with Node 22 and 24, and in its `old-node` job `npm ci`, `npm run
build` and `node --test e2e/old-node.e2e.js` on ubuntu with Node 20.
`.github/workflows/semantic.yml` runs `node --test e2e/semantic.e2e.js` on ubuntu with Node 22
for every push to main and pull request, and on ubuntu, macOS and Windows with Node 22 and 24
weekly and by hand; it caches the model, keyed on its pinned revision.
`test/node-floor.test.js` keeps `engines.node` (`>=22.13`, for `node:sqlite`), the lockfile's
root entry and that matrix in step.

## Unsupported Node version

- **Reached by**: the bin, `dist/cli.js`, on a Node older than 22.13 (`npx -y mnemos-mcp` reaches
  users on any Node): it imports nothing at the top, checks `process.versions.node` against
  `MIN_NODE` (`src/node-version.ts`) and, instead of loading the server (which needs
  `node:sqlite`), runs `src/unsupported-node.ts`: an MCP server whose instructions and every
  tool's `isError` result say which Node mnemos needs, which one runs, and to upgrade or pin
  `mnemos-mcp@0.3`; it also prints that to stderr.
- **Tests**: `test/unsupported-node.test.js`: `supportsNode` on versions either side of 22.13;
  `MIN_NODE` matches `engines.node`; the bin is `dist/cli.js` with a node shebang; the message
  names both versions, upgrading and `mnemos-mcp@0.3`; e2e on the current Node with a faked old
  version (`serveUnsupportedNode("20.17.0")` in a child): handshake, `serverInfo`, instructions,
  the same six tool names the real server lists (checked against `dist/cli.js` on this Node),
  and every tool answering `isError` with the message. `e2e/old-node.e2e.js` runs the bin itself
  on Node 18 (the MCP SDK's minimum) and 20 in CI's old-node job; `test/old-node-ci.test.js`
  keeps that job's matrix and steps in place.
- **Tickets**: mnemos-nru; mnemos-gts.13 (Node 18 in CI)

## Local index store

- **Reached by**: the background title indexer (see Background title indexing), the page
  fetcher (see Background page fetching) and `semantic_search`, which reads it;
  `src/index-store.ts` (`IndexStore.open`, `cacheDir`, `indexFile`). One `node:sqlite` file in

  directory (`~/Library/Caches/mnemos`, `%LOCALAPPDATA%\mnemos\Cache`,
  `$XDG_CACHE_HOME/mnemos` or `~/.cache/mnemos`), beside the model's `models/` and the

  rebuild of an older or newer `schema_version`; a garbage file, an overwritten header and a
  damaged page deep in the file (found by `PRAGMA quick_check` at open) moved aside and rebuilt;
  `isCorrupt`; bookmark upsert (unchanged rows untouched, a new `text_hash` drops the vector,
  descriptions kept when omitted, cleared when null), delete and sync, with a URL's page and chunks kept until its last bookmark
  goes; same URL in two folders as two rows; Float32 BLOB round trip bit for bit; nearest
  bookmarks and chunks by dot product; pages and chunks; a model or revision change dropping every
  vector and keeping the rows; the lease acquired, renewed, expired, taken over and released
  between two stores on one file. `test/index-open-race.test.js` (child processes on one cache
  directory, released at one shared moment): several processes opening one new index at once
  all open it, none fails with "database is locked", and the file ends in WAL mode.
  `test/index-store-rollback.test.js`: a write transaction that SQLite rolls back itself on a

## semantic_search

- **Reached by**: tool `semantic_search(query, folder?, limit?)`; `semanticSearch` in
  `src/semantic.ts`, given the embedder, the indexer and the fetcher. A bookmark scores the
  better of its title vector's similarity to the query (`passage` / `query` prefixes) and its
  page's best chunk's; bookmarks matching every query word as `search_bookmarks` does are
  keyword hits, always returned and ranked first; the rest are kept only above the embedder's
  cutoff (a floor, a margin over the median title, a window below the best; see the next
  section). Results carry `score`, `matched_on` (`title`, `page` with a `snippet`, or
  `keyword`) and the bookmark fields; `count_above_threshold` counts them before `limit`
  (default 20, cap 100). The `folder` filter matches as `list_folder_contents` does. Every
  answer has a `status`: `search` (`semantic` or `keyword`), `indexing`, `progress`
  (`titles x/N · pages y/N`), `embedder` (installing, downloading n%, loading, ready,
  unavailable), `fetching_disabled`, `fetching`, `page_states`, `browser` when pages wait for
  one, and a `note` when the answer is keywords only or titles are still being embedded; a
  one-time `notice` when page fetching first starts. The query's vector is waited for at most 3 s (`QUERY_EMBED_TIMEOUT_MS`), then
  the answer falls back to keyword hits. Each call runs the indexer's `checkForChanges()`.
  Page text is matched only for pages this process's `MNEMOS_SKIP_DOMAINS` /
  `MNEMOS_SKIP_FOLDERS` leave fetchable, by its bookmark's URL and the `final_url` a redirect
  took its fetch to (the index is shared, and its fetcher lease holder applies its own lists):
  a page they cover is found by its title alone, with no snippet. Only the last hop is stored,
  so a skipped domain the fetch only passed through is not caught.

## Index freshness

- **Reached by**: the background fetcher's refill (`src/fetcher.ts`: `pageResult`, `backoffMs`,
  `Fetcher`'s `applyPolicy`) and the indexer's sync (`IndexStore.syncBookmarks`). Every stored
  outcome sets `pages.next_attempt_at`: an `ok`, `needs_login` or fetch-skipped page is due
  `REFRESH_MS` (30 days) after its fetch, a `failed` one after `BACKOFF_STEPS_MS` (1 h, 6 h,
  1 d, 7 d, then 30 d) by its `fail_count`, which carries over until a fetch succeeds; a
  `no_content` page (no text even in the browser) has none and is final. A re-fetched page whose `content_hash` is unchanged is not cut or embedded again.
  The fetch policy (`fetchConfig`, as JSON in the `fetch_policy` meta key) is compared at each
  refill; when it changed, `needs_login` pages and pages the fetch itself skipped (a redirect
  to a skipped domain, a private address) are due at once. Pages a skip list covers are
  `skipped` with no next attempt and their chunks dropped, and go back to `pending` once no
  skip list covers them (the list edited, or the bookmark moved out of a skipped folder). A
  deleted bookmark's row goes at the indexer's next run, with its page and chunks unless
  another bookmark has the URL. The fetcher, indexer and store take a `now` clock.
- **Tests**: `test/index-freshness.test.js` (in process, an injected clock, a fake fetch and a
  counting fake embedder on one index): an ok page not fetched at 29 days and fetched at 31,
  its unchanged text not embedded again and a changed one embedded; a failing page retried
  exactly at 1 h, 6 h, 1 d, 7 d, 30 d and 30 d and not a minute before, then recovering with
  its count reset; `needs_login` and a redirect's skip not fetched again at 29 days, fetched
  once on a policy change and once 30 days later; a deleted bookmark's page and chunks gone,
  a URL still bookmarked in another folder kept and never the deleted one fetched; skip-list
  edits skipping pages (chunks dropped, not fetched 31 days on) and un-skipping them.
  `e2e/semantic.e2e.js` (see Suites), with the real model: a bookmark added to the file while
  the server runs is found by its title, a deleted one (with page text) is gone from results,
  and a renamed one is found by its new title, each waited for on the status.

  different skip lists taking the lease in turn: each change of holder applies the new holder's

  the `needs_login` and fetch-skipped pages once and the old holder fetches nothing; nothing

## Page chunks

- **Reached by**: the indexer (`src/indexer.ts`), after each title pass and, debounced, after the
  fetcher stores a page (`Fetcher`'s `onPage` calls `Indexer.pagesChanged()`, a run of the page
  pass alone); `src/chunk.ts` (`chunkText`, `estimateTokens`, `chunkEmbeddingText`). An `ok`
  page whose `content_hash` is not the `pages.chunked_hash` its chunks came from (schema version
  3) is cut into chunks of about 350 tokens (estimated from characters by script: ¼ token per
  ASCII character, 1 per Chinese/Japanese/Korean one, 0.4 otherwise) on paragraph and sentence
  boundaries (`Intl.Segmenter`), a longer sentence at a space or a character, each chunk starting
  with about 15% of the one before, at most 40 per page; a page that lost its text (no longer
  `ok`, and not just `failed`) loses its chunks. Chunks without a vector are embedded as
  `passage`, the bookmark's title (150 characters at most) on the line before, 8 at a time with
  a yield between; a page whose title is no longer the `pages.chunked_title` its vectors were
  embedded with (schema version 4: its bookmark renamed, or deleted and another bookmark's title
  now the page's) has its chunks embedded again, uncut, and a vector embedded with a title the
  page no longer has is not stored. `semantic_search` ranks a bookmark by the better of its title and its page's
  best chunk (`matched_on: "page"` with a snippet that starts near the first query word); the
  progress line's `pages y/N` counts pages whose chunks are all embedded.
